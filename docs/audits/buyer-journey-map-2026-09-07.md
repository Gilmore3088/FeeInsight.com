## 2. Transactional flows

### 2a. Registration

1. **Entry** — guide sidebar `Link href="/register?intent=fee-alert&category=<c>"` (`app/(public)/guides/[slug]/page.tsx:639`); `/login` "Sign up" → `/register` (`app/(auth)/login/page.tsx:113`); `/subscribe` → `/register` (`app/subscribe/page.tsx:104,152`); `SubscribeButton` fallback → `/register?from=/subscribe` (`app/subscribe/subscribe-button.tsx:38`).
2. **Page** — `app/(auth)/register/page.tsx:13` `RegisterPage()` — no `searchParams` prop; `intent`, `category`, `from` are discarded. Redirects signed-in users to `/account` (l.15). Renders `<RegisterForm />` with no props (l.118).
3. **Form** — `app/(auth)/register/register-form.tsx:54-68` `handleSubmit` → `register(formData)`; on success `router.push(result.redirect)`.
4. **Action** — `app/(auth)/register/actions.ts:27` `register()`:
   - validates email/password/name (l.41-54);
   - `hashPassword` (l.56);
   - **`getStripe().customers.create({ email, name })` — hard dependency; any throw returns "Registration failed" (l.58-68)**;
   - transaction: `INSERT INTO users (… role 'viewer', stripe_customer_id, subscription_status 'none', institution_name, institution_type, asset_tier, state_code, job_role)` + `INSERT INTO sessions` (l.76-92); on DB error deletes the Stripe customer (l.94-97) and maps unique-violation to "already exists" (l.99-101);
   - sets `fsh_session` cookie, 24h (l.105-112);
   - **returns `{ success: true, redirect: "/account" }` unconditionally (l.114)**. `/account/welcome` is never the destination.
5. **Landing** — `/account` (`app/account/page.tsx`). Nothing on it references the fee category or intent. The user must re-find "Find Your Institution" in the nav.
6. **`/account/welcome`** — only reached from Stripe `success_url`. It re-asks the profile (`welcome-steps.tsx:139-182`, posting to `updateProfile` in `app/account/actions.ts:11`) and never reads `intent`, `category`, or `success`.

### 2b. Subscription

1. **`/subscribe`** (`app/subscribe/page.tsx`) — signed-in non-premium user sees `SubscribeButton priceId={STRIPE_PRO_PRICE_ID | STRIPE_ANNUAL_PRICE_ID} mode="subscription"` (l.95-101, 143-149). Price IDs come from env (l.17-19); no `.env.example` exists in the repo, so which prices (and whether they carry a trial) is Stripe-side and not determinable from source.
2. **`createCheckoutSession`** (`lib/stripe-actions.ts:8-34`) — requires a session (throws "Not authenticated" → button pushes `/register?from=/subscribe`, `subscribe-button.tsx:37-38`); creates a Checkout Session with `customer: user.stripe_customer_id` (always set by registration), `metadata: { user_id, email }`, `success_url: /account/welcome?success=true`, `cancel_url: /subscribe` (l.20-31). No `from`/`instId` is carried in metadata or the success URL.
3. **Stripe Checkout** — hosted.
4. **Webhook `POST /api/webhooks/stripe`** (`app/api/webhooks/stripe/route.ts`):
   - verifies signature (l.14-24); idempotency via `INSERT INTO stripe_events … ON CONFLICT DO NOTHING` (l.31-37);
   - `checkout.session.completed` → `UPDATE users SET subscription_status='active', role='premium', stripe_customer_id=… WHERE (email = … OR username = …) AND role NOT IN ('admin','analyst')` (l.40-57). Match is by `session.customer_email || session.metadata.email` — because checkout passes `customer:`, `customer_email` is null and the update relies entirely on `metadata.email` (set at `stripe-actions.ts:29`). `metadata.user_id` is not used.
   - `customer.subscription.updated` → `subscription_status = mapStripeStatus(sub.status)` (l.60-69); statuses `incomplete`/`paused` map to `"none"` (l.119-132), which revokes access via `canAccessPremium` while `role` stays `premium`.
   - `customer.subscription.deleted` → `'canceled'` (l.72-80); `invoice.payment_failed` → `'past_due'` (l.83-95). Neither resets `role`.
5. **Fallbacks** — `/account/welcome` `activateIfPaid` (`welcome/page.tsx:37-58`) and `/account` (`account/page.tsx:33-53`) both call `stripe.subscriptions.list({status:"active"})` and set `active`/`premium` if the webhook was missed.
6. **`subscription_status` → access** — `lib/access.ts:8` `subscription_status === "active"` is the only thing that flips every `canAccess*` helper. `past_due` and `canceled` both fully lock the user out of `/pro` (`app/pro/layout.tsx:50-52` → `/subscribe`); `/account` still labels a `past_due` user "Pro Account … Active" plus a "Past Due" pill (`account/page.tsx:203-219`) only when `isPro`, which is false for `past_due` — so the past-due card is unreachable and they see the free "Unlock the full platform" card instead.
7. **First `/pro` screen** — `/pro` (`app/pro/page.tsx:43-45`) → `/pro/monitor` (H1 "Institutional Monitor"). The subscriber only reaches it by choosing "Dashboard" in `CustomerNav` after `/account/welcome` → `/account`.

## 4. The one change per journey

**Anonymous consumer → make `/register` finish the guide's job.** Read `intent`, `category`, `from` in `RegisterPage` and pass them to `RegisterForm` as hidden fields; when `intent=fee-alert`, render the consumer variant (name/email/password only, copy about alerts, no "About your organization"); have `register()` return `redirect: /institutions?fee=<category>&intent=fee-alert` instead of `/account`. Reason: the guide is the only consumer entry with a clear ask, and today every word of it is dropped the moment the reader clicks (`register/page.tsx:13`, `actions.ts:114`). This also removes the professional-form friction that is the single most likely abandonment point for a consumer.

**Registered consumer → add the save action.** Put a "Save {institution} — alert me when {fee} changes" button on `/institution/[id]` (server action or `fetch("/api/alerts", {institution_id, fee_categories:[fee]})`, pre-filled from `?fee=`), and render `getAlertSubscriptions(user.id)` on `/account` with remove buttons. Reason: the whole data layer, API, and guide-side panel already exist (`lib/data-store/alerts.ts`, `api/alerts/route.ts`, `saved-institutions-panel.tsx`) and are wired to nothing; this one control turns them on and makes "come back" meaningful. (The dispatcher, Break 3, is the necessary follow-up before the e-mail promise is honest.)

**Professional → land the buyer in Hamilton with their reason intact.** Change `success_url` to `/pro/monitor?success=true` (and carry `instId`/`from` from `/pro/layout.tsx:51` through `/subscribe` into checkout `metadata` and the success URL), and make `/account/welcome` redirect premium users to `/pro/monitor`. Reason: the paid product is `/pro`; today a new subscriber is bounced through a wizard that re-asks their profile, shows free-tier data, and exits to `/account` and `/fees` (`welcome-steps.tsx:292-303`), so activation depends on them finding "Dashboard" in the nav on their own.
